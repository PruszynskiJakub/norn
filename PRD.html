psdd — CLI for the SDD process

2026-10-13 · Jakub Pruszyński

psdd is a CLI that the developer's LLM calls to run work through the organisation's spec-driven process, with GitHub labels as the only source of truth.

Purpose and principles

  • The LLM is the operator and psdd is the process. The agent asks psdd what to do next and which skill to use, does the work, then asks psdd to record the result.
  • GitHub is the source of truth. State lives in issue and PR labels, native "blocked by" relations, comments and branches. psdd keeps no state of its own.
  • The developer's own gh is used. No separate auth or server. Every label change, comment, PR and merge is made as the user.
  • psdd owns transitions, skills own content. Only psdd changes labels, and it allows only valid transitions. The skill for each state tells the agent how to do the work.
  • Work is scoped to one story. Every session declares the story it works on.

Story flow

Phase 1 needs a human present. Triage either accepts an issue into needs-refinement or closes it as not planned, with the reason in a comment. Clarification only happens when refinement turns up questions. Once slice issues exist, the story's label follows its slices. When every slice PR is merged into the story branch, the story branch is reviewed and QA'd. Story QA is always done by a human. Failed review or QA is fixed straight on the story branch with the implement skill and goes back to needs-review. Finally the owner merges the story PR into main, and GitHub closes the story through the PR link.

Slice flow

blocked and ready-for-agent follow GitHub's native "blocked by" relations. Both failure states go back to implementation. A slice in merge-queue is merged into the story branch by an agent, which resolves conflicts if needed.

Branches, PRs and ownership

Slices merge into the story branch, and only the story's owner merges the story into main.

  • The story owner is also the owner of all its slices.
  • Fixes after story-level changes-requested or qa-failed are committed straight onto the story branch.

Worktrees

The story and each slice have their own worktree for the life of their branch. Every phase runs in a fresh subagent with empty context, working in that worktree.

  • Story worktree: refine, clarify, plan, slice, story review, story QA and story fixes run here.
  • Slice worktree: implement, review, QA and merge run here, each as a new subagent.
  • The briefing carries the process; skills carry the craft. Skills know nothing of psdd, labels, branches or worktrees: each ends on a result (a spec, a verdict, a breakdown). The briefing says what to read, where the work is committed and pushed, which commands create slices and PRs, and which finish command each result maps to.
  • psdd says where to work. The take briefing names the worktree path and branch. If the worktree is missing, it gives the command to create it for the tool in use.
  • Base branch: a slice worktree starts from the story branch. The story worktree starts from main. psdd makes the story branch on GitHub and slices merge there, so a new branch starts from origin/<base>, fetched first, without tracking it; a branch that exists only on GitHub is fetched and checked out with its commits; and a local branch that is also on GitHub is fast-forwarded inside the new worktree (git merge --ff-only origin/<branch>: local commits ahead of GitHub are kept, and a diverged branch gets its worktree with the failing merge as the signal). A branch already checked out in another checkout gets no create command; psdd names that checkout instead.
  • Paths are absolute and git runs as git -C <main checkout>, so the commands work from any directory, including another worktree.

  • psdd init adds .agents/worktrees/ to .gitignore.
  • psdd next removes the worktrees of closed items (herdr worktree remove or git worktree remove): a slice's once it has merged into the story branch, the story's once the story has merged into main. psdd done does not, because the merge agent runs inside the slice worktree. psdd never removes the worktree it runs in, and a removal that fails is reported, not fatal.
  • A worktree left behind by a session whose claim went stale is kept: the session may only be slow, and its commits are there. The next holder is told to check git status before starting.

Configuration

Team settings live in a committed .agents/psdd.config.json. Each developer picks their worktree tool in a gitignored .agents/psdd.config.local.json, which wins over the team file.

// .agents/psdd.config.json (committed)
{
  "baseBranch": "main",
  "worktrees": { "provider": "auto" },
  "claims": { "staleAfter": "2h" },
  "deliver": { "maxParallel": 2, "maxFixRounds": 3 }
}

// .agents/psdd.config.local.json (gitignored, per developer)
{ "worktrees": { "provider": "herdr" }, "notifications": "auto" }
  • Provider is auto, herdr, claude-code or git. auto uses the detection in the Worktrees table, in order: herdr first, then Claude Code, then plain git.
  • Environment variables are a safety check. If the provider is herdr but HERDR_ENV is not set, psdd refuses and tells the agent to start from a herdr pane or switch the provider in the local file.
  • Labels are fixed and not configurable, so every repo in the organisation works the same way.
  • psdd init creates the team file with defaults, taking baseBranch from the repository's default branch, and adds the local file to .gitignore.
  • The worktree location is fixed at .agents/worktrees/, like the labels.

Concurrency: git-ref claims

A claim is a git ref created through the GitHub API, which either succeeds or fails atomically. Label changes and comments on an issue happen only while holding its claim.

claim:    gh api -X POST repos/:owner/:repo/git/refs \
            -f ref=refs/psdd/claims/<issue> -f sha=<claim commit>
          201 = claim held, go ahead
          422 = someone else holds it, skip or retry
release:  gh api -X DELETE repos/:owner/:repo/git/refs/psdd/claims/<issue>
  • Only one agent can win. Two subagents can't take the same slice, because the second ref creation fails. Checking a label first cannot guarantee that.
  • The in-progress label mirrors the ref. It shows the claim in GitHub. The ref is the real lock.
  • Claims are held for the whole step, e.g. all of implement on a slice, and released when handing over to the next state.
  • Stale claims. The ref points at a small commit recording holder, session ID and timestamp. psdd treats a claim older than 2 hours as abandoned and lets another session take it over.
  • Refreshing a claim. psdd take on an issue the same session already holds briefs again and moves the claim's timestamp forward (the ref is force-updated to a new claim commit). Long steps re-run it, e.g. after each implement commit, so a slow session is not taken for crashed.
  • Transition first, then follow-ups. psdd done checks its preconditions (a story leaving slicing gets its branch first), changes the labels and releases the claim. The automatic transitions after it, such as unblocking slices and opening the story PR, are best effort: a failure is reported, and psdd next repeats them.

Artifacts

Each story has one document, built up across refine, clarify and plan: .agents/specs/<story issue ID>-<slug>/spec.md.

  • Slices are GitHub issues only. They have no markdown files.
  • Open questions live in a section of spec.md. When a question is answered it is removed, and the decision is written into the section of the spec it affects.
  • All comments are posted as the user through gh. Review and QA notes and the reason for needs-human go in comments. On each transition psdd posts a short comment linking to the spec at its commit.

Skills and setup

psdd init sets psdd up in a client project. It installs the skills with npx skills <psdd repo> into a root skills/ directory, symlinks them into .claude/skills/, and creates .agents/specs/. psdd briefings then tell the agent which skill to invoke by name.

The step skills lean on three reference skills that psdd also installs: interview (refine, clarify, plan, resolve), and codebase-design (plan) and tdd (implement), adapted from mattpocock/skills (MIT). The spec's Behaviour items are numbered user stories; slices, review and QA check against them by number, and the Plan names the seams that implement tests at.

Sessions

A session always works on one declared story. An unattended session is, for example, a Claude Code session whose main agent hands out next actions to subagents.

  1. The main agent asks psdd for every actionable item on the story, each with its skill and worktree.
  2. It starts a fresh subagent per item, in that item's worktree (under herdr, a new herdr agent in the worktree's pane). Unblocked slices run in parallel.
  3. Each subagent claims its issue, follows the skill, and asks psdd to make the transition. The next phase gets a new subagent.
  4. When a mode:hil slice reaches needs-qa, the session sets needs-human and carries on with other slices that aren't blocked by it.
  5. A human records the QA result through their agent, which calls psdd.

The main agent never edits labels directly. It only calls psdd.

Which session holds a claim. psdd keeps no state, so the session comes from the environment, first match wins: PSDD_SESSION, then CLAUDE_CODE_SESSION_ID, then herdr:<HERDR_PANE_ID>, then <hostname>:<main checkout root>. It never depends on the current directory, because an agent moves between the main checkout and worktrees within one session. Under the plain git provider, psdd next names a PSDD_SESSION=psdd-<issue>-<random> to start each agent with, with a fresh random suffix each time it lists the item. Agents on one machine are separate sessions, and a new agent on an item whose claim went stale takes it over as a new session rather than passing for the old holder.

Known limit: claude-code provider. Claude Code subagents inherit their parent's CLAUDE_CODE_SESSION_ID; the session id, CLAUDE_CODE_CHILD_SESSION and CLAUDE_PID are the same in the parent and its subagents. So under the claude-code provider the deliver orchestrator and all its subagents are one psdd session, and psdd cannot stop one subagent finishing, releasing or escalating another's item. Isolation relies on psdd next listing held items as "held by this session", so the orchestrator never hands an item out twice. For per-agent isolation, use herdr: each herdr agent is its own Claude Code session.

Unattended delivery: the deliver skill

deliver <story id> runs a story unattended from implementation until it needs a human. The user starts it once slicing is done.

  1. Ask psdd for work: psdd next <story>.
  2. Start a fresh subagent per actionable item in its worktree (a herdr agent under herdr), at most 2 at a time.
  3. Wait for subagents to finish (under herdr, with herdr agent wait --until done|blocked), then go back to step 1.
  4. When an item gets needs-human, psdd notifies the user (see Notifications) and the orchestrator carries on with everything not blocked by it.
  5. Once all slices are merged into the story branch, run story review the same way, plus implement fixes if review asks for changes.
  6. Stop when the story reaches needs-qa (always a human) or when only items waiting for a human remain. End with a report: what is done, what is waiting, and who needs to act.

Rules for the orchestrator

  • Never do a phase's work itself. Every phase gets a new subagent.
  • Never touch labels, branches or PRs. Only call psdd.
  • Never take an item flagged needs-human.

Limits

  • Parallelism: at most 2 subagents at once (deliver.maxParallel).
  • Fix rounds: after 3 rounds of changes-requested or qa-failed on the same issue, psdd sets needs-human instead of sending it back to implement (deliver.maxFixRounds). psdd counts rounds from the issue's label history, so it keeps no state of its own.

When nothing is left to do, psdd next says so explicitly:

Story #123 "Rate limiting": nothing left that you can do.

Waiting for a human:
  - #129 QA in mode:hil.
  - #131 escalated: "Redis client times out in tests" (3 fix rounds reached).

Stop here and report to the user. psdd has already notified them.

Notifications

psdd sends local notifications itself, so they fire whatever agent tool is in use and do not depend on the orchestrator remembering.

Events (more may be added later)

  • needs-human is set: an escalation, a mode:hil slice reaching QA, an issue hitting the fix-round limit, or the story reaching story QA.
  • deliver stops: psdd next reports nothing left to do, with a summary of what is waiting.

The title says who must act on what ("psdd: #131 needs you"). The body gives the reason and the issue link.

CLI

psdd answers in prose written as instructions to the agent. The agent reports outcomes and psdd chooses the next state. It is written in Node/TypeScript and installed through npx.

  • Outcomes, not states. The agent never names a label. It reports what happened (approve, fail), and psdd makes the transition.
  • Issue as an argument. Every command takes the story or issue number explicitly. There is no session state.
  • Fixed response order: where you are, what to do now (including the skill to invoke), how to finish (exact commands), what not to do.
  • Refusals are instructions. They say why the call was refused and what to do instead.
  • Attended steps are marked as attended in the briefing, which names the skill that runs them. There is no extra gate for now.
  • --json is available for scripts. Prose is the default.

A refusal

Slice #131 is already held by another session (since 14:02).
Do not work on it. Run psdd next 123 and pick a different item.

Automatic transitions psdd makes

  • Slice issues created: story goes to implementation.
  • A slice merges: dependents with no open blockers go from blocked to ready-for-agent.
  • The last slice PR merges into the story branch: story goes to needs-review.
  • An issue reaches its fix-round limit: it gets needs-human instead of going back to implement.

Recommendations

psdd does not require these tools, but they make working with it faster.

  • herdr: the preferred worktree provider. Each phase runs as its own herdr agent in the worktree's pane, deliver waits on agents with herdr agent wait, and notifications show inside herdr. psdd detects it with HERDR_ENV=1 and picks it first in auto mode.
  • Ghostty: the recommended terminal to run herdr and the agents in.
