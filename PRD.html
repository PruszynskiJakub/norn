shepherd — CLI for the SDD process

2026-10-13 · Jakub Pruszyński

shepherd is a CLI that the developer's LLM calls to run work through the organisation's spec-driven process, with GitHub labels as the only source of truth.

This document holds the vision and the way of working. The domain terms it uses (story, slice, step, claim, briefing, outcome, needs-human, fix round and the rest) are defined in CONTEXT.md; a new concept here adds its entry there in the same change.

Purpose and principles

  • The LLM is the operator and shepherd is the process. The agent asks shepherd what to do next and which skill to use, does the work, then asks shepherd to record the result.
  • GitHub is the source of truth. State lives in issue and PR labels, native "blocked by" relations, comments and branches. shepherd keeps no state of its own.
  • The developer's own gh is used. No separate auth or server. Every label change, comment, PR and merge is made as the user.
  • shepherd owns transitions, skills own content. Only shepherd changes labels, and it allows only valid transitions. The skill for each state tells the agent how to do the work.
  • Work is scoped to one story. Every session declares the story it works on.

Story flow

Phase 1 needs a human present. Triage either accepts an issue into needs-refinement or closes it as not planned, with the reason in a comment. Clarification only happens when refinement turns up questions. Once slice issues exist, the story's label follows its slices. When every slice PR is merged into the story branch, the story branch is reviewed and QA'd, by an agent and then by a person (see QA). Failed review or QA is fixed straight on the story branch with the implement skill and goes back to needs-review. Finally the owner merges the story PR into main, and GitHub closes the story through the PR link.

Slice flow

blocked and ready-for-agent follow GitHub's native "blocked by" relations. Both failure states go back to implementation. A slice in merge-queue is merged into the story branch by an agent, which resolves conflicts if needed.

QA

An agent always QAs first; a person follows when the item needs one.

StateSkillWhoRuns for
needs-qaauto-qaAn agent, unattendedEvery slice and every story
needs-human-qaqaA person with their agent (attended)Slices in mode:hil and every story
  • The agent collects the evidence; a person decides. An auto-qa failure goes straight to qa-failed. Only a person passes a mode:hil slice or a story.
  • auto-qa runs the app as a user would and records, per criterion, what it ran, what it saw and the evidence. What only a person can check comes from the slice's verifier reason; the agent lists it with whatever it could prepare. On a mode:afk slice it escalates what it cannot check.
  • Evidence is the shepherd done note on the issue, with files from --evidence <dir> pushed to shepherd/qa/<issue> and embedded at their commit.
  • qa starts from that note: the person's agent runs the app locally and walks them through what is left. The person may fail any criterion, with a repro.
  • The person's own remarks are tied to criteria and fail them. A remark outside the criteria becomes a follow-up issue by default; the person may pull it into this item or drop it.
  • needs-human in either state means an escalation, cleared by resolve.

Branches, PRs and ownership

Slices merge into the story branch, and only the story's owner merges the story into main.

LevelBranchWorktreePR targetsWho merges
Story<id>-<slug>.agents/worktrees/<id>-<slug>mainThe story owner
Slice<id>-<slug>-<sliceid>.agents/worktrees/<id>-<slug>-<sliceid>story branchAn agent, resolving conflicts if needed
  • There is one PR per slice.
  • The story owner is also the owner of all its slices.
  • Fixes after story-level changes-requested or qa-failed are committed straight onto the story branch.
  • The slug is recorded once. shepherd writes shepherd: slug <slug> in its first comment on a story and derives the branch, slice branches, worktrees and spec path from it, so renaming the story on GitHub changes none of them.
  • A story's slices are its sub-issues labelled type:slice in this repository. Other sub-issues a person attaches are ignored.
  • A slice merge is accepted only when its PR targets the story branch.

Worktrees

The story and each slice have their own worktree for the life of their branch. Every phase runs in a fresh subagent with empty context, working in that worktree.

  • Story worktree: refine, clarify, plan, slice, story review, story QA and story fixes run here.
  • Slice worktree: implement, review, QA and merge run here, each as a new subagent.
  • The briefing carries the process; skills carry the craft. Skills know nothing of shepherd, labels, branches or worktrees: each ends on a result (a spec, a verdict, a breakdown). The briefing says what to read, where the work is committed and pushed, which commands create slices and PRs, and which finish command each result maps to.
  • shepherd says where to work. The take briefing names the worktree path and branch. If the worktree is missing, it gives the command to create it for the tool in use.
  • Base branch: a slice worktree starts from the story branch, and the story worktree from main, as they are on GitHub. A branch that already exists keeps its commits and is brought up to date; one checked out in another checkout gets no create command, and shepherd names that checkout instead.
  • The commands work from any directory, including another worktree.
ToolPicked in auto modeNew agent per phase
herdrInside herdrA new herdr agent in the worktree's pane
Claude CodeInside Claude CodeA new subagent told to work in the worktree. Claude Code's built-in worktree isolation is not used
gitOtherwiseA new agent session started in the worktree, as its own session, as shepherd next lists it
  • shepherd init adds .agents/worktrees/ to .gitignore.
  • shepherd tidy removes worktrees of closed items with the tool in use, never the one it runs in.
  • When the story PR is merged and GitHub has not closed the story, e.g. with a base branch other than the default, shepherd next closes it. It also removes state labels left on closed issues.
  • A worktree left behind by a session whose claim went stale is kept: the session may only be slow, and its commits are there. The next holder is told to check git status before starting.

Housekeeping: shepherd tidy

All cleanup is shepherd tidy. It removes what belongs to closed issues: QA evidence branches, worktrees, merged slice and story branches, and claim refs. Anything with uncommitted or unpushed work is named, not removed. It is idempotent; --dry-run only lists. deliver runs it when it starts and stops, drive when a story finishes. Nothing is cleaned up at merge: the owner merges the story on GitHub, where shepherd does not run.

Configuration

Team settings live in a committed .agents/shepherd.config.json. Each developer picks their worktree tool in a gitignored .agents/shepherd.config.local.json, which wins over the team file. claims.staleAfter and deliver.maxFixRounds bind everyone's claims and rounds, so shepherd reads them from the team file only. Set in the local file, they are ignored with a warning; a team staleAfter below 10m is raised to 10m with a warning. Commands still run in both cases.

// .agents/shepherd.config.json (committed)
{
  "baseBranch": "main",
  "worktrees": { "provider": "auto" },
  "claims": { "staleAfter": "2h" },
  "deliver": { "maxParallel": 2, "maxFixRounds": 3 }
}

// .agents/shepherd.config.local.json (gitignored, per developer)
{ "worktrees": { "provider": "herdr" }, "notifications": "auto" }
  • Provider is auto, herdr, claude-code or git. auto uses the detection in the Worktrees table, in order: herdr first, then Claude Code, then plain git.
  • The environment is a safety check. If the provider is herdr but shepherd is not running inside herdr, shepherd refuses and tells the agent to start from a herdr pane or switch the provider in the local file.
  • Labels are fixed and not configurable, so every repo in the organisation works the same way.
  • shepherd init creates the team file with defaults, taking baseBranch from the repository's default branch, and adds the local file to .gitignore.
  • The worktree location is fixed at .agents/worktrees/, like the labels.

Concurrency: claims

A claim is taken on GitHub in one step that either succeeds or fails, so only one session can hold it. Label changes and comments on an issue happen only while holding its claim.

  • Only one agent can win. Two subagents can't take the same slice: the second one is refused. Checking a label first cannot guarantee that.
  • The in-progress label mirrors the claim, so it shows in GitHub. The claim is the real lock.
  • Claims are held for the whole step, e.g. all of implement on a slice, and released when handing over to the next state. A person's step is claimed too: shepherd next lists an item waiting for a person that a session holds as "held by <session> (since hh:mm)", and offers no hand-off for it.
  • Stale claims. A claim records its holder, session and time. shepherd treats a claim older than 2 hours as abandoned and lets another session take it over; two sessions taking over at once cannot both win.
  • Taking over your own stopped session. shepherd take <issue> --takeover takes over a claim of the same GitHub user at any age, e.g. a session closed partway through refinement, with the same note to check git status. Without the flag, take refuses and names the command. It never takes another user's claim. Agents in deliver share their user, so the flag is for people, who know the other session has stopped.
  • Refreshing a claim. shepherd take on an issue the same session already holds briefs again and moves the claim's time forward. Long steps re-run it, e.g. after each implement commit, so a slow session is not taken for crashed.
  • Transition first, then follow-ups. shepherd done checks its preconditions (a story leaving slicing gets its branch first), changes the labels and releases the claim. The automatic transitions after it, such as unblocking slices and opening the story PR, are best effort: a failure is reported, and shepherd next repeats them.

Artifacts

Each story has one document, built up across refine, clarify and plan: .agents/specs/<story issue ID>-<slug>/spec.md.

  • Slices are GitHub issues only. They have no markdown files.
  • Open questions live in a section of spec.md. When a question is answered it is removed, and the decision is written into the section of the spec it affects.
  • All comments are posted as the user through gh. Review and QA notes and the reason for needs-human go in comments. On each transition shepherd posts a short comment linking to the spec at its commit.

Skills and setup

shepherd init sets shepherd up in a client project. It installs the skills with npx skills <shepherd repo> into a root skills/ directory, symlinks them into .claude/skills/, and creates .agents/specs/. shepherd briefings then tell the agent which skill to invoke by name.

The step skills lean on three reference skills that shepherd also installs: interview (refine, clarify, plan, resolve), and codebase-design (plan) and tdd (implement), adapted from mattpocock/skills (MIT). The spec's Behaviour items are numbered user stories; slices, review and QA check against them by number, and the Plan names the seams that implement tests at.

Sessions

A session always works on one declared story. An unattended session is, for example, a Claude Code session whose main agent hands out next actions to subagents.

  1. The main agent asks shepherd for every actionable item on the story, each with its skill and worktree.
  2. It starts a fresh subagent per item, in that item's worktree (under herdr, a new herdr agent in the worktree's pane). Unblocked slices run in parallel.
  3. Each subagent claims its issue, follows the skill, and asks shepherd to make the transition. The next phase gets a new subagent.
  4. When a slice reaches needs-human-qa, shepherd notifies the user and the session carries on with slices not blocked by it.
  5. A person records their QA result through their agent, which calls shepherd. Under herdr, that agent works in the item's worktree pane, like every other phase: with each item waiting for a person (needs-human-qa or needs-human), shepherd next lists how to hand it to an agent there if the user does it now, or, inside that worktree, says to take it in the current session. Under the other providers the person's agent works from wherever it runs.

The main agent never edits labels directly. It only calls shepherd.

Which session holds a claim. shepherd keeps no state, so it tells sessions apart by their environment, never by the current directory: an agent moves between the main checkout and worktrees within one session. Under the plain git provider, shepherd next gives each agent it lists a session of its own, fresh each time, so a new agent on an item whose claim went stale takes it over rather than passing for the old holder.

Known limit: claude-code provider. Claude Code subagents share their parent's session, so under the claude-code provider the deliver orchestrator and all its subagents are one shepherd session, and shepherd cannot stop one subagent finishing, releasing or escalating another's item. Isolation relies on shepherd next listing held items as "held by this session", so the orchestrator never hands an item out twice. For per-agent isolation, use herdr: each herdr agent is its own session.

Unattended delivery: the deliver skill

deliver <story id> runs a story unattended from implementation until it needs a human. The user starts it once slicing is done.

  1. Run shepherd tidy once at the start, then ask shepherd for work: shepherd next <story>.
  2. Start a fresh subagent per actionable item in its worktree (a herdr agent under herdr), up to the free slots shepherd next gives (see Limits).
  3. Wait for subagents to finish (under herdr, with herdr agent wait --until done|blocked), then go back to step 1.
  4. When an item gets needs-human, shepherd notifies the user (see Notifications) and the orchestrator carries on with everything not blocked by it.
  5. Once all slices are merged into the story branch, run story review and story auto-qa the same way, plus implement fixes if either asks for changes.
  6. Stop when the story reaches needs-human-qa (always a person) or when only items waiting for a person remain, also when a person is already doing them. Run shepherd tidy, then end with a report: what is done, what is waiting, and who needs to act. Delivery does not wait on a person's work: the person's drive session offers deliver again when they finish.

Rules for the orchestrator

  • Never do a phase's work itself. Every phase gets a new subagent.
  • Never touch labels, branches or PRs. Only call shepherd.
  • Never take an item flagged needs-human or in needs-human-qa.
  • If the user runs drive in the orchestrator's session, do that step with them, then go back to the loop: the deliver they asked for still stands. drive does not offer deliver again from a session already running it.

Limits

  • Parallelism: at most 2 subagents at once (deliver.maxParallel). shepherd next counts the user's agents already running on the story (items held by their sessions) and offers only the free slots: "at most 1 at a time (1 of your agents is running, the limit is 2)". At the limit it lists the ready items without start commands and says to wait for one to finish. A teammate's agents and a person's work do not count. shepherd does not know which orchestrator started an agent, so two orchestrators of the same user share the limit; marking the running orchestrator is issue #26.
  • Fix rounds: after 3 rounds of changes-requested or qa-failed on the same issue, shepherd sets needs-human instead of sending it back to implement (deliver.maxFixRounds). shepherd counts rounds from the issue's label history, so it keeps no state of its own.

When nothing is left to do, shepherd next says so explicitly:

Story #123 "Rate limiting": nothing left that you can do.

Waiting for a human:
  - #129 needs human QA (mode:hil).
  - #131 escalated: "Redis client times out in tests" (3 fix rounds reached).

Stop here and report to the user. shepherd has already notified them.

Notifications

shepherd sends local notifications itself, so they fire whatever agent tool is in use and do not depend on the orchestrator remembering.

Events (more may be added later)

  • A person is needed: needs-human is set (an escalation or an issue hitting the fix-round limit), or a mode:hil slice or the story reaches needs-human-qa.
  • deliver stops: shepherd next reports nothing left to do, with a summary of what is waiting. Items a session already holds are left out; if a person is already doing everything that waits, nothing is sent.

The title says who must act on what ("shepherd: #131 needs you"). The body gives the reason and the issue link.

Delivery is chosen per developer in .agents/shepherd.config.local.json with "notifications":

CLI

shepherd answers in prose written as instructions to the agent. The agent reports outcomes and shepherd chooses the next state. It is installed into the project and run through npx.

  • Outcomes, not states. The agent never names a label. It reports what happened (approve, fail), and shepherd makes the transition.
  • Issue as an argument. Every command takes the story or issue number explicitly. There is no session state.
  • Fixed response order: where you are, what to do now (including the skill to invoke), how to finish (exact commands), what not to do.
  • Refusals are instructions. They say why the call was refused and what to do instead.
  • Attended steps are marked as attended in the briefing, which names the skill that runs them. There is no extra gate for now.
  • --json is available for scripts. Prose is the default.

A refusal

Slice #131 is already held by another session (since 14:02).
Do not work on it. Run shepherd next 123 and pick a different item.

Automatic transitions shepherd makes

  • Slice issues created: story goes to implementation.
  • A slice merges: dependents with no open blockers go from blocked to ready-for-agent.
  • The last slice PR merges into the story branch: story goes to needs-review.
  • An issue reaches its fix-round limit: it gets needs-human instead of going back to implement.

Recommendations

shepherd does not require these tools, but they make working with it faster.

  • herdr: the preferred worktree provider. Each phase runs as its own herdr agent in the worktree's pane, deliver waits on agents with herdr agent wait, and notifications show inside herdr. shepherd picks it first in auto mode.
  • Ghostty: the recommended terminal to run herdr and the agents in.
